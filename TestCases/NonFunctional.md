# Test Cases: Non-Functional (Visual, API, Network Mocking, Accessibility)

**Source requirement:** Requirement items #5 (Visual regression testing), #6 (API-level tests alongside E2E tests), #7 (Accessibility checks), and #8 (intercept and mock a network request).

**Scope deviation note:** Unlike `Login.md`, `Logout.md`, and `Checkout.md`, this file is **not** organized around a single screen or user flow. Items #5–#8 in the requirement are cross-cutting quality-assurance *techniques* (visual diffing, API/network validation, network mocking, accessibility scanning) that can be applied to any page or flow in the app, not a distinct feature of SauceDemo itself. Per the manual-test-case-writer skill's instruction to split/say so when a requirement spans multiple features, these four techniques are grouped into one file — each case anchors the technique to a concrete, already-covered page or flow (login, inventory, checkout) rather than inventing a new screen, and each case is otherwise independent of the others.

**Target app:** https://www.saucedemo.com

**Assumptions (original, at time of manual-test-case authoring):**
- **TC-NFR-001 (Visual Regression):** The inventory/products page immediately after login is chosen as the subject because it is the most stable, deterministic post-login screen in the app (no cart state, no dynamic checkout data). No baseline screenshot existed yet in this repo; the automation stage would need to establish the initial baseline on first run and treat subsequent runs as comparisons against it. Exact tooling (Playwright's built-in `ToHaveScreenshotAsync` via `Microsoft.Playwright.NUnit`) was left to the automation stage to confirm is available/appropriate for this Playwright/NUnit version.
- **TC-NFR-002 (API-level test):** SauceDemo is a client-rendered demo app and, unlike the requirement's own alternate example (a "RealWorld" app with a conventional REST API), it was unverified whether SauceDemo exposes any conventional backend REST API distinct from static assets. The specific request to validate was marked `[TBD: identify during automation via live network inspection]`.
- **TC-NFR-003 (Network interception/mocking):** Same caveat as TC-NFR-002 — the specific request to intercept was marked `[TBD: identify during automation via live network inspection]`. Login submission was proposed as a candidate for mocking an error response, unverified until real traffic was inspected.
- **TC-NFR-004 (Accessibility):** The requirement names `@axe-core/playwright`, an npm/JavaScript package. This project is C#/.NET (per CLAUDE.md), so that exact package cannot be used directly. A .NET-compatible axe-core binding was flagged as needed, to be resolved during automation.

**Confirmed against the live app and automation tooling (2026-08-18) — replaces all `[TBD]` markers above:**

- **TC-NFR-001 (Visual Regression) — API confirmed, not what was assumed:** `Microsoft.Playwright.NUnit` 1.52.0 does **not** expose a screenshot-comparison assertion. Confirmed via reflection against the installed `Microsoft.Playwright.dll`: `IPageAssertions` only has `ToHaveTitleAsync`/`ToHaveURLAsync`, and `ILocatorAssertions` has no `ToHaveScreenshotAsync` member — the JS/TS Playwright binding's `page.toHaveScreenshot()` has not been ported to this version of the .NET binding. Automation instead uses a custom pixel-diff comparison (`TestProject1/Utilities/VisualBaseline.cs`, built on `SixLabors.ImageSharp`, already a project dependency) against a baseline PNG committed at `TestProject1/Baselines/inventory-page.png`. The baseline was established on an initial run and a second run was executed and confirmed passing (pixel-diff within the 1% tolerance) against that committed baseline — see `TestProject1/Tests/NonFunctionalTests.cs`.
- **TC-NFR-002 / TC-NFR-003 (Network) — confirmed via live traffic inspection:** SauceDemo is a static SPA with **no conventional backend REST API**. Login form submission and checkout form submission are both purely client-side (validated against data baked into the page's JS bundle) — no XHR/fetch fires for either, so there is nothing to intercept there. The only runtime network calls beyond static assets/images are: (a) a Google Fonts stylesheet request to `https://fonts.googleapis.com/css2?...`, fired on every page load, which returns a real `200 text/css` response with `@font-face` rules — this is the request used for both TC-NFR-002 (validate real response) and TC-NFR-003 (mock a failure); and (b) telemetry beacons to `events.backtrace.io` that consistently return `401` with what appears to be a placeholder/demo token — not a meaningful contract to assert against, so not used.
- **TC-NFR-004 (Accessibility) — package confirmed to exist and resolve:** `Deque.AxeCore.Playwright` (NuGet, version `4.13.0`) is the .NET-compatible axe-core binding used in place of the JS-only `@axe-core/playwright`. Confirmed to resolve from nuget.org and to wrap the real axe-core engine (`AxeResult.TestEngine` reports `"axe-core" 4.13.0` at scan time). `Deque.AxeCore.Commons.AxeResultItem.Impact` uses the same severity vocabulary as axe-core's own JS API: `"minor"`, `"moderate"`, `"serious"`, `"critical"` — confirmed via reflection and live scan output. "Critical/serious" in the Expected Result column below maps directly to those two string values.
- **TC-NFR-004 — genuine product defect found, not a test/tooling problem:** the accessibility scan of the **inventory page** (post-login) finds a real, reproducible violation: the product-sort `<select class="product_sort_container" data-test="product-sort-container">` has no accessible name (axe rule `select-name`, impact `critical` — no wrapping `<label>`, no `for`-linked `<label>`, no `aria-label`, no `aria-labelledby`, no `title`). This is flagged as a **product bug candidate** against the live SauceDemo app, not a defect in the automation. Per this repo's self-healing policy, the corresponding automated test (`InventoryPage_AccessibilityScan_HasNoCriticalOrSeriousViolations` in `TestProject1/Tests/NonFunctionalTests.cs`) is left asserting zero critical/serious violations and is expected to **fail** until the app fixes this (or until the team decides to explicitly accept/waive this specific rule). The login-page variant of this scan (logged out) finds **no** critical/serious violations and passes.
