# Test Cases: Login

**Source requirement:** Manual QA coverage for the Login feature of the target app under test, per CLAUDE.md's default (no feature-specific requirement was supplied by the user, only the target URL).
**Target app:** https://www.saucedemo.com

**Assumptions:**
- No Page Objects or existing tests exist yet in `TestProject1/` (only the scaffold `UnitTest1.cs` sample) and no prior `TestCases/Login.md` exists, so this is authored fresh rather than extended from existing coverage.
- The live SauceDemo page could not be visually inspected this session (client-rendered SPA; static fetch only returned an empty `<div id="root">` shell), so exact on-screen copy (field labels, button text, error message wording) is **unverified**. All expected results are written around observable behavior, with literal copy marked `[TBD: confirm exact text]`. The automation stage (which has live Playwright/Bash access) should confirm and fill in exact strings.
- Test data references credentials by role, backed by `TestProject1/TestSettings.cs` (`.env` locally / Azure Pipelines secret variables in CI — see `.env.example` and CLAUDE.md's "Credentials & Sensitive Data" section) rather than literal values, per project policy. The **exact current roster of usernames** (which accounts exist, whether the locked-out account still triggers a lockout, etc.) is unverified this session and should be confirmed against the live site (or by inspecting real Page Objects once created) before/during automation — do not treat `.env.example`'s values as ground truth without that check.
- "Successful login" is assumed to mean redirection to the inventory/products page (standard SauceDemo post-login landing page); the exact URL/path is unverified and should be confirmed during automation.
- Field identifiers (`Username`, `Password`, `Login` button) are referred to by their conventional SauceDemo names; exact `data-test` attributes/selectors are unverified and are the automation engineer's responsibility to confirm, not this document's.
- TC-LOGIN-008 (added later, Data-Driven) reuses the same unverified-copy caveats as TC-LOGIN-002/004 above; it does not introduce any new assumption beyond consolidating those outcomes into one parameterized case.
